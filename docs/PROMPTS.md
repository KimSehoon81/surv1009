# Day별 실행 프롬프트

Claude Code(Opus · 노력 "높음")에 그대로 붙여넣는 프롬프트입니다. 작업 항목의 세부 내용은 `docs/WORKPLAN.md`에 있고, 여기에는 **그날의 목표, 읽을 범위, 설계 지침, 검증 방법**만 담았습니다.

## 사용법

1. Claude Code에서 이 저장소로 **새 세션**을 엽니다. 모델 Opus, 노력 "높음".
2. 아래에서 그날 Day의 코드블록을 통째로 복사해 붙여넣습니다. (`/day`를 입력해도 같은 프롬프트를 찾아 실행합니다. **`/day 4`이면 다음 Day 4개를 연달아 진행** — 실측상 Day 1개 ≈ 20%라 한 창에 4개, 무거운 Day(D05·D07·D13·D16)가 섞이면 3개)
3. 사용량이 80%대가 되면 `마무리해`라고 입력합니다.
4. 이월이 있으면 다음 날 프롬프트를 그대로 써도 Claude가 이월부터 처리합니다.
5. 그래픽을 넣은 날은 프롬프트 끝에 `그래픽 넣었어`를 한 줄 덧붙입니다.

## 이 프롬프트들이 Opus·높음에 맞춘 방식

- **목표와 완료 기준을 먼저** 줍니다. 무엇을 끝내야 하는지가 분명하면 높은 추론 노력이 탐색이 아니라 설계 판단에 쓰입니다.
- **읽을 범위를 제한**합니다. 문서·코드 탐색은 사용량을 가장 많이 쓰는 부분입니다.
- **설계 지침에는 이유를 붙였습니다.** 이유를 알면 지침이 맞지 않는 상황에서도 의도에 맞게 판단합니다.
- **계획은 한 번, 짧게** 쓰게 합니다. 사용자 확인을 기다리지 않아 왕복 비용이 들지 않습니다.
- 반복되는 공통 규칙(절차·절약·커밋)은 매 세션 자동으로 읽히는 `CLAUDE.md`에 두어 프롬프트에서 뺐습니다.
- 각 프롬프트의 "main에 바로 푸시해도 된다"는 세션 브랜치 대신 main으로 반영하라는 **명시적 허용**입니다(빼면 세션 브랜치까지만 푸시합니다).

### D01 · 프로젝트 골격과 자리표시자 에셋

```text
오늘은 D01 「프로젝트 골격과 자리표시자 에셋」이다. CLAUDE.md 일일 절차대로 진행하고, 끝나면 main에 바로 푸시해도 된다.

읽을 범위: docs/WORKPLAN.md의 "### D01" 절과 2장(확정 사항·폴더 구조), PRD §10 §12. 그 밖의 문서는 읽지 않는다.
목표: 이후 44일 동안 바꾸지 않을 골격을 만든다. 오늘 정한 구조가 매일의 작업 비용을 좌우하므로, 기능보다 구조의 단순함과 일관성을 우선한다.

설계 지침
- Phaser 3는 정확한 버전으로 고정한다(^ 범위 금지). 재현 가능한 빌드가 매일 새 컨테이너에서 같은 결과를 내야 하기 때문이다.
- vite.config의 base는 './'로 둔다(D45 배포 대비).
- 화면: 논리 960×540, 창 크기에서 정수 배율 floor(min(w/960,h/540))을 계산해 적용하고, 1 미만이 되면 FIT 비정수로 떨어진다. pixelArt·roundPixels 켬.
- systems/clock.ts: 전투 로직은 모두 이 시계의 scaledDelta만 쓴다. 일시정지·히트스톱·슬로모·카드 판정 0.3배가 전부 여기 한 곳의 배율로 처리되어야 이후 Day들이 충돌하지 않는다.
- 에셋 존재 여부는 런타임 404로 판단하지 말고, tools/gen-asset-list.mjs가 public/assets를 스캔해 만든 목록(src/assets/available.json, git 무시)을 쓴다. predev·prebuild·pretest 스크립트로 자동 실행.
- 자리표시자는 Graphics로 그려 generateTexture 후 400×400 시트(4×4, 100×100, 앞 10칸)로 프레임을 등록한다. 실제 PNG와 같은 키·같은 프레임 구조여야 교체가 코드 수정 없이 된다. 프레임마다 번호를 찍어 애니메이션 재생이 눈에 보이게 한다.
- core/rng.ts: mulberry32 같은 작은 시드 RNG, fork(name)로 파생 스트림. Phaser import 금지.

검증: npm run check 통과, vite build 산출물 크기 기록, 빈 전투 씬에 자리표시자 캐릭터 1개.
시작할 때 5줄 이내로 계획만 쓰고 바로 구현한다. 지시보다 나은 방법이 있으면 이유를 한 줄 남기고 그쪽으로 간다.
```

```text
오늘은 D02 「애니메이션 시스템, 플레이어 이동, 바닥 타일, 에셋 검사」다. CLAUDE.md 일일 절차대로 진행하고, 끝나면 main에 바로 푸시해도 된다.

설계 지침
- 애니메이션 키는 `${id}_${action}`, 등록은 진영별 동작 목록(아군 6/적 5/NPC 3)과 프레임 수(data/assets.json: 아군 6, 적·NPC 5)를 데이터로 받아 한 함수로. 이후 90종 유닛이 같은 함수를 쓴다. 프레임 수가 적으니 frameRate는 동작별 data(예: 걷기 8, 공격 12)로.

- 동작 상태 머신은 우선순위 + 최소 재생 시간(치명타 0.3초, 스킬 0.4초)으로. 공격·방어·스킬·치명타는 오늘은 디버그 키로만 트리거한다.
- 스프라이트 원점은 (0.5, 0.92) — ASSETS.md의 발 기준점(50, 92)과 일치해야 그림을 바꿔도 발이 미끄러지지 않는다.
- 바닥: 화면을 덮는 T01 TileSprite의 tilePosition을 카메라 스크롤에 맞추고, T02는 64px 그리드의 시드 기반 청크 패치로 얹는다. 무한 맵이지만 생성 비용은 화면 크기에 비례해야 한다.
- check-assets.mjs: 의존성 없이 PNG 헤더(IHDR)만 읽어 크기 확인. 기대 크기는 manifest와 같은 규칙(src/data/assets.json)에서 계산하고, 파일명 규칙에 안 맞는 파일·크기 불일치·투명 채널 없음(색 형식 6이 아님)을 목록으로. 변환은 tools/art/postprocess.py가 하므로 여기서 이미지를 고치지 않는다.

검증: npm run check, 디버그 키로 6동작 전환 확인, 일부러 잘못 만든 PNG(크기·이름 틀림)를 검사 도구가 잡아내는지 확인 후 삭제.
계획은 5줄 이내로 쓰고 바로 진행한다.
```

### D03 · 적, 오브젝트 풀, 공간 분할, 스포너

```text
오늘은 D03 「적, 오브젝트 풀, 공간 분할, 스포너」다. CLAUDE.md 일일 절차대로 진행하고, 끝나면 main에 바로 푸시해도 된다.
```

### D07 · 카드 시스템 코어 로직

```text
오늘은 D07 「카드 시스템 코어 로직(순수 함수)」이다. CLAUDE.md 일일 절차대로 진행하고, 끝나면 main에 바로 푸시해도 된다.

읽을 범위: WORKPLAN "### D07" 절, PRD §5.1, §5.3, §5.3.1, §5.4의 (c).
목표: Phaser 없이 테스트만으로 카드 규칙 전부가 검증된다. 이 게임의 핵심 재미 2번이고, 이후 UI·연출은 이 모듈을 호출만 한다.

설계 지침
- 상태는 불변 데이터 + 순수 전이 함수(state, action, rng) → {state, events}. 이벤트 목록(drawn, judged, consumed, sealGained…)을 UI가 받아 연출한다. 이렇게 해야 연출과 규칙이 섞이지 않는다.
- 성공률 계산 순서: 기본 30 + 조합(2장 +5/3장 +10) + 정보(+10, 1회) + 행운·업그레이드·숙련 − 환경 보정(방공망 등, 지금은 0) → [0, 60]으로 자르기 → 인장이면 100. 각 항을 분해해 반환해 HUD가 내역을 보여줄 수 있게 한다.
- 조합 매칭: 제출 카드 태그의 다중집합에서 레시피 중 가장 많은 카드를 쓰는 것을 고른다(동률이면 data의 priority). 매칭 안 된 카드는 효과 없음. 이 해석을 combos.json 상단 주석 필드에 남긴다.
- 실패 시 소멸 카드: 등급 일반 < 희귀 < 전설 중 최저, 동률이면 제출 순서 첫 번째.
```
